# ForReal app

Phase 2 of ForReal: the Android app. It reads bank payment SMS on the phone, turns each one
into a transaction on the backend (without the message text or the exact amount), asks the user
"shop or person?" and "what did you buy?" in a notification, and lets them tag and correct
payments in the app.

Flutter (Dart) for everything except a small Kotlin module that receives SMS. Android only for
now (minSdk 26, applicationId `com.forreal.app`). The screens use no Android-only Flutter
packages, so they are ready for an iOS build once an iOS capture module exists.

## Setup

You need Flutter stable (built and tested with Flutter 3.44 / Dart 3.12), the Android SDK and a
JDK 17 or 21.

```bash
cd app
flutter pub get
flutter analyze
flutter test
flutter build apk --debug --dart-define=API_BASE_URL=http://10.0.2.2:8000
```

`lib/data/db/database.g.dart` is generated by drift and is checked in. After changing
`lib/data/db/database.dart`, regenerate it:

```bash
dart run build_runner build
```

Kotlin unit tests (the sender filter):

```bash
cd android && ./gradlew :app:testDebugUnitTest
```

No Flutter on your machine? Everything above also runs in Docker:

```bash
docker run --rm -v "$PWD/..":/work -w /work/app ghcr.io/cirruslabs/flutter:stable \
  sh -c "flutter pub get && flutter analyze && flutter test && flutter build apk --debug"
```

On an ARM machine (Apple silicon) the image is ARM, but Android's `aapt2` is an x86-64 binary, so
`flutter build apk` needs the x86-64 C libraries inside the container first. Analyze and test work
without this.

```bash
sed -i 's/^Types: deb$/Types: deb\nArchitectures: arm64/' /etc/apt/sources.list.d/ubuntu.sources
printf 'Types: deb\nURIs: http://archive.ubuntu.com/ubuntu/\nSuites: noble noble-updates noble-security\nComponents: main universe\nArchitectures: amd64\nSigned-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg\n' \
  > /etc/apt/sources.list.d/amd64.sources
dpkg --add-architecture amd64 && apt-get update && apt-get install -y libc6:amd64 libstdc++6:amd64 zlib1g:amd64
```

### Configuration

| What | How |
| --- | --- |
| Backend address | `--dart-define=API_BASE_URL=http://host:8000` (no `/api/v1`). Default `http://10.0.2.2:8000`, which is the development machine as seen from the Android emulator |
| Notice version | `noticeVersion` in `lib/features/consent/notices.dart`. Change it whenever a notice changes meaning |

Plain HTTP is allowed in **debug builds only** (`android/app/src/debug/res/xml/network_security_config.xml`).
A release build has no such configuration and refuses cleartext traffic, so it needs an `https://` backend.

## Release signing

Debug builds are signed with the debug key and need no setup. A release build is signed with your
own keystore, named in `android/key.properties`. Both files are gitignored. Without
`key.properties` a release build stops with "Release signing is not set up" rather than falling
back to the debug key.

Create the keystore once. Run this yourself in a terminal; it asks for a password and your name:

```bash
docker exec -it forreal-flutter keytool -genkeypair -v \
  -keystore /work/app/android/upload-keystore.jks \
  -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

(With a JDK on the host, run `keytool` directly with `-keystore app/android/upload-keystore.jks`.)

Then tell the build about it:

```bash
cp android/key.properties.example android/key.properties
# edit android/key.properties: storePassword and keyPassword are the password you just chose
```

Build:

```bash
flutter build apk --release --dart-define=API_BASE_URL=https://your-host
# build/app/outputs/flutter-apk/app-release.apk
```

Keep a copy of the keystore and its password somewhere safe outside this folder. Every update of
the app must be signed with the same key: if it is lost, installed copies can no longer be
updated, only uninstalled and reinstalled, which wipes their local data.

## Run against a local backend from a physical phone

1. Put the phone and the computer on the same Wi-Fi. Find the computer's LAN address, for example
   `192.168.1.20` (`ipconfig getifaddr en0` on macOS).
2. Let the backend answer on that address. In `backend/.env`:
   ```
   ALLOWED_HOSTS=localhost,127.0.0.1,192.168.1.20
   OTP_ECHO_IN_RESPONSE=1
   ```
   then `cd backend && docker compose up --build`. The compose file already binds port 8000 on all interfaces.
   Check from the phone's browser: `http://192.168.1.20:8000/health/` should show `{"status": "ok"}`.
3. Enable USB debugging on the phone, connect it, and run a debug build:
   ```bash
   flutter run --dart-define=API_BASE_URL=http://192.168.1.20:8000
   ```
4. With `OTP_ECHO_IN_RESPONSE=1` the app fills in the sign-in code for you. Otherwise read
   it from the backend log (`docker compose logs web | grep OTP`).

On an emulator, skip steps 1 and 2 and use the default address. Send a test bank message with:

```bash
adb emu sms send HDFCBK "Sent Rs.300.00
From HDFC Bank A/C *0000
To SAMPLE  PAYEE
On 02/08/26
Ref 000000000000
Not You?
Call 18002586161/SMS BLOCK UPI to 7308080808"
```

(Use today's date in the `On` line: a date more than three days from the arrival day is ignored in
favour of the arrival day, and the server refuses dates in the future.)

## Layout

```
lib/
  main.dart, app.dart      start-up, lifecycle, notification taps
  bootstrap.dart           binds the platform pieces (the only place that knows it is Android)
  background.dart          the two entry points that run without the UI
  core/                    config, router and guard, providers, formatting, feature flags
  core/theme/              design tokens: AppColors (light and dark), AppText, spacing and radii
  core/widgets/            shared widgets: AppButton, AppChip, AppToggle, PaymentRow, AppBottomNav ...
  data/                    API client and repositories, typed models, drift database, local store
  capture/                 TransactionSource, AndroidSmsSource, templates, parser, pipeline
  features/<feature>/      session, consent notices, auth, onboarding, home, transaction, payee,
                           items, sync, notifications, location, settings, parser_gaps
android/app/src/main/kotlin/com/forreal/app/capture/   the Kotlin SMS module
```

Widgets are thin. Rules live in services with unit tests: `SyncService`, `PromptService`,
`CapturePipeline`, `MessageParser`, `PayeeService`, `ItemsService`, `SessionController`, `ApiClient`.

## Design system

The screens follow the Figma file (design system page, node 3:2). Everything visual comes from
tokens in `lib/core/theme/`; widgets contain no hard-coded colours.

- **Colour carries meaning.** Marigold (`brand`) means something needs you. Green (`real`) is only
  for things confirmed by a real payment or by you. An AI guess is never green: it is a dashed
  outline with a spark, muted, and labelled "guessed". Primary buttons are ink. Destructive actions
  are soft red.
- **Light and dark** share every widget; only the palette changes, and it follows the system
  setting. The welcome screen is ink in both.
- **Type** is Bricolage Grotesque for display and titles and DM Sans for everything else, through
  `AppText`. The app follows the system text size up to 1.3.
- **Shared widgets** live in `lib/core/widgets/` and are imported through `lib/core/widgets.dart`.
- **Feature flags** are constants in `lib/core/feature_flags.dart`. `merchantInsightsEnabled` is
  `false`, which hides the "Insights for shops" toggle in onboarding and under You.
- **Discover and Insights** are tabs with a "coming soon" state. They arrive in Phase 4.

Golden images of the shared widgets and five screens, in light and dark, are in
`test/widgets/goldens/`. After an intended visual change, regenerate them:

```bash
flutter test --update-goldens test/widgets/golden_test.dart
```

They are rendered on Linux (the Docker image above). Text renders slightly differently on macOS and
Windows, so run the golden tests on Linux, or regenerate before comparing on another platform.

Other checks in `test/widgets/`: every screen at 360 dp wide with text scale 1.3 in both themes
(`layout_test.dart`), and 48 px labelled tap targets (`accessibility_test.dart`). Token values and
contrast ratios are in `test/core/theme_test.dart`.

## How capture works

```
 SMS arrives
     │
     ▼
 SmsReceiver (Kotlin)            sender not in the allowed bank codes → dropped, body never read
     │  sender is a bank
     ▼
 Native queue (Kotlin)           SQLite, body encrypted with an Android Keystore key; survives process death
     │
     ├─ app on screen ───────────► EventChannel ─► Dart, in the running app
     │
     └─ app in background/killed ─► WorkManager ─► CaptureWorker ─► headless FlutterEngine
                                                    runs captureBackgroundMain() in lib/background.dart
     ▼
 CapturePipeline (Dart)          parse with the downloaded templates
     │   debit   → local_transactions (parsed fields only; the message text is discarded)
     │   credit  → ignored
     │   no match → unparsed_messages (device only, newest 200)
     ▼
 SyncService (Dart)              POST transactions/batch/  (payee name, date, day part, amount band, ref)
     ▼
 PromptService (Dart)            notification according to the server's `ask`
```

- **Kotlin does three things: receive, filter by sender, queue.** There is no parsing in Kotlin.
  The allowed sender codes are written by Dart whenever templates are downloaded
  (`CaptureControl.setAllowedSenders`). A sender such as `AD-HDFCBK` or `VM-HDFCBK-S` matches the
  code `HDFCBK`: the two-character operator prefix and the one-character suffix are ignored and the
  rest must equal the code exactly (`SenderFilter.kt`, mirrored in `lib/capture/sender_matcher.dart`).
- **Nothing is captured before the private-analytics consent.** Capture is a native switch that is
  off by default, turned on when the consent is granted and off again when it is withdrawn, at
  which point the queue and the local payment data are wiped.
- **Background processing uses WorkManager with a headless FlutterEngine**, the same pattern as the
  firebase_messaging background handler. No foreground service. Work survives a reboot because
  WorkManager persists it, and the queue is on disk. On Android 12 and later the work is expedited;
  below that it is ordinary work, because expedited work there would run as a foreground service.
  If the upload fails for lack of a connection, a second request waits for connectivity. A periodic
  request (hourly, needs a connection) retries anything left over and refreshes the templates.
- **One channel surface**: `forreal/capture` (methods) and `forreal/capture/messages` (events),
  wrapped by `AndroidSmsSource`, which implements `TransactionSource` and `CaptureControl`. Nothing
  else in `lib/` touches platform channels.
- **History import** asks Kotlin for inbox messages from allowed senders in a date range, in pages.
  It first looks only at sender and date, then reads the text of matching messages only.
- **Idempotent**: `client_txn_id` is a UUIDv5 of sender, timestamp and text, so capturing or
  importing the same message again produces the same id, which the server answers with `duplicate`.

## What leaves the phone

| Stays on the phone | Sent to the backend |
| --- | --- |
| SMS text (discarded after parsing) | Payee name as the bank wrote it |
| Exact amount (encrypted local database) | Amount band: under 50, 50 to 200, 200 to 500, above 500 |
| Account digits (never stored) | Date, part of the day |
| Unparsed bank messages (newest 200, debug screen only) | Bank reference (the server stores only its HMAC) |
| Precise location (never requested) | Location rounded to 3 decimals, only with the location consent |

The local database is SQLCipher-encrypted (drift on `package:sqlite3` with `source: sqlcipher`).
Its key is 32 random bytes generated on first run and kept, with the JWTs, in
`flutter_secure_storage`. The app refuses to open the database if the bundled SQLite is not
SQLCipher. Android backup is disabled for the app.

## Permissions

| Permission | Why | When it is asked |
| --- | --- | --- |
| `RECEIVE_SMS` | Receive bank payment messages as they arrive | Onboarding step 1, after the notice and rationale |
| `READ_SMS` | Optional import of past bank messages. Same prompt as above | Same prompt |
| `INTERNET` | Talk to the ForReal backend | Not a runtime permission |
| `ACCESS_COARSE_LOCATION` | Approximate location, to identify the shop and name the area. Foreground only | Onboarding step 3, after the location notice |
| `POST_NOTIFICATIONS` | "Shop or person?" and "what did you buy?" prompts (Android 13+) | Onboarding step 4 |
| `RECEIVE_BOOT_COMPLETED` | Keep the 8 pm summary notification scheduled after a reboot | Not a runtime permission |

Added by libraries, none of them a runtime prompt: `ACCESS_NETWORK_STATE` (WorkManager and
connectivity), `WAKE_LOCK` (WorkManager), `VIBRATE` (notifications). WorkManager also declares
`FOREGROUND_SERVICE`; the app manifest removes it, so a foreground service cannot be started at all.

Not requested, on purpose: `ACCESS_FINE_LOCATION`, `ACCESS_BACKGROUND_LOCATION`, notification-listener
access, `SEND_SMS`, contacts, exact alarms, any foreground-service permission.

If the SMS permission is refused the app still works: the home screen shows a "Capture is off"
banner. Tapping it asks again, or opens the app's system settings once Android stops showing the prompt.

## Manual test script (real phone)

Use a debug build pointed at your backend (see above), on a phone whose SIM receives HDFC Bank
UPI debit messages (the only seeded template). Have a second way to see the server:
`http://<host>:8000/admin/`.

1. **Fresh install.** Uninstall any old build, install, open. Expect the dark welcome screen.
2. **Sign in.** *Get started*, enter the number, *Send code*, enter the code (prefilled when
   the backend echoes it), *Verify*. Expect onboarding "1 of 5". In the admin, a Device row exists for the user.
3. **Consents.**
   - Step 1: *Allow and continue*, then allow in Android's SMS prompt. (*Not now* explains that this
     step is required and offers sign-out.)
   - Step 2: leave the toggle off, *Skip for now*. Step 3: *Allow location* and allow in the prompt
     (choose *Approximate* if offered). Step 4: *Turn on notifications*. Step 5: *Start fresh*,
     *Finish setup*.
   - Expect *Payments* with "Nothing here yet" and no "Capture is off" banner. In the admin, consent
     history shows `private_analytics` and `location` granted with notice version `2026-10-v1`.
4. **Real payment.** Put the app in the background (or swipe it away) and pay a small amount by UPI
   from the HDFC account to a shop.
5. **Notification.** Within a minute or so of the bank SMS, expect "Paid ₹N to NAME" / "New here.
   Shop or person?" with *Shop* and *Person*. In the admin the transaction exists with an amount band and no amount.
6. **Confirm shop.** Tap *Shop*. Expect "Is this a shop or a person?" with *A shop* selected.
   *Continue*, *Add a new shop*, enter the name, pick what kind of place, *Save shop*. Expect the
   payment to show the shop name and a dashed "guessed" chip, never a green one. Because this is within 10 minutes of the payment and the app is
   open, the transaction and the merchant get a rounded location and, shortly after, a locality.
7. **Next payment auto-resolves.** Pay the same shop again with the app closed. Expect a different
   notification: "Paid ₹N at SHOP" / "For ITEM?" with *Yes*, *Something else*, *Not a shop*.
8. **Tag.** Tap *Yes* without opening the app. Open the app: the row shows a green check and the item.
9. **Correct a tag.** Open the first payment, *Edit what you got*, deselect the guess, pick another
   item or use *Add your own*, raise the quantity to 2, *Save*. Expect green chips on the payment.
   Then *Not a shop* → *A person* → *Continue*: both payments become "Person · private" and lose
   their items. Change it back through *This is actually a shop*.
10. **Withdraw location.** You → *Location* off, confirm. In the admin, the
    user's transactions have no location and no locality. Pay again: the new transaction has no location.
11. **Export.** You → *Export my data*. Expect the share sheet with `forreal-export.json`;
    open it and check it lists the payments with amount bands only.
12. **Delete account.** You → *Delete account and all data* → confirm. Expect the welcome screen. In the
    admin the user, their transactions, consents and devices are gone. Reopen the app: still signed
    out, and a new bank SMS produces no notification.

Also worth checking on a real phone, because unit tests cannot: a payment while the phone is in
Doze (screen off for a while), a payment right after a reboot before the app is opened, refusing
the SMS permission ("Capture is off" appears, app usable), dark mode on every screen, and airplane mode during a payment (it uploads and
notifies when the connection returns, unless more than 30 minutes have passed).

## Live end-to-end test

`test/integration/live_backend_test.dart` drives a real backend through the app's own code: sign
in, consents, template download, a bank SMS text through the parser, upload, shop confirmation with
location, the next payment resolving by itself, tagging, corrections, restore on a fresh install,
location withdrawal, export and account deletion. It is skipped unless you point it at a backend
running with `OTP_ECHO_IN_RESPONSE=1`:

```bash
LIVE_API_BASE_URL=http://localhost:8000 flutter test test/integration/live_backend_test.dart
```

It creates a throwaway user and deletes the account at the end. It does not cover anything that
needs Android: the SMS receiver, WorkManager, notifications, permissions.

## Known limits

- One bank template is seeded (HDFC UPI debit). Other banks need templates added in the backend
  admin; unmatched bank messages show up, masked, on the debug *Parser gaps* screen.
- Exact amounts exist only in the local database. After a reinstall or sign-out, payments restored
  from the server show the amount range.
- OEM battery managers (Xiaomi, Oppo, Vivo and others) can delay or block background work for apps
  the user has not exempted. The payment is still processed the next time the app is opened.
